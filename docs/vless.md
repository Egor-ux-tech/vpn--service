# VLESS

VLESS + Reality is a second, **parallel** VPN protocol alongside WireGuard — not a
replacement. Every existing WireGuard device/server/peer/routing-profile row and code
path is unchanged; VLESS is additive at every layer (new columns with safe defaults,
new tables, new services, protocol branches in the handful of places that genuinely
need one). See `docs/wireguard.md` for the WireGuard side, which this document assumes
as context.

## Why VLESS, and why Reality

VLESS is one of the protocols the Happ client (the intended primary client for this
service — see the VLESS/Happ compatibility research this design is based on) officially
supports; WireGuard is not. Reality (XTLS) is VLESS's TLS-camouflage transport,
authenticating the *server* to clients via a single long-lived X25519 keypair — no
per-client keypair, no IP allocation, and a fundamentally different identity model from
WireGuard's per-peer keypairs: a VLESS client's identity is a UUID (a bearer
credential), generated by the backend, never exchanged as key material.

## Data flow

```
Telegram (user picks "VLESS")
  → bot: POST /api/v1/devices {protocol: "vless"}
    → backend: DeviceService._provision_vless
      → VPNServerService.pick_best_available(VPNProtocol.VLESS)
      → generate uuid4() (backend-owned identity, like IP allocation is for WireGuard)
      → XrayAgentProvider.create_user(server_config, uuid, device_id, flow)
        → xray-agent (HMAC-signed HTTP) → Xray HandlerService gRPC (AddUserOperation)
      → create VLESSCredential row (status=active)
      → SubscriptionLinkService.create_or_rotate(device)   ← unchanged, protocol-agnostic
    → response: subscription_url (+ QR) — config_text/qr_code_base64 are None; there is
      no separate downloadable artifact, the subscription link IS the config

Happ (or any client): user adds the subscription URL
  → GET /sub/{token}
    → SubscriptionDeliveryService._authorize() — unchanged, protocol-agnostic
    → device.protocol == VLESS → load active VLESSCredential row(s) + their
      VPNServer/VLESSServerConfig → VLESSFormatter
  → response: one `vless://...` line per active credential (see docs/xray-agent.md's
    "user lifecycle" table and vless_formatter.py for the exact grammar)

Happ connects directly to the VLESS node — the backend is not in this hop, exactly as
a WireGuard client never routes through the backend either.
```

## Database design

Deliberately does **not** force VLESS data into `VPNPeer`/`VPNProfile`/`VPNServer`'s
WireGuard-specific columns — see each model's own docstring for the reasoning:

```
VPNServer.protocol            NEW column: wireguard | vless (default wireguard,
                               backfilled — see the migration). Existing WG columns
                               (agent_base_url/public_key/endpoint/internal_network)
                               untouched, and are filled with an explicit
                               "unused-for-vless" placeholder for VLESS rows rather
                               than repurposed.

vless_server_configs          NEW table, 1:1 with a VPNServer row where protocol=vless.
                               xray_agent_base_url, port, reality_public_key (NOT the
                               private key — see docs/xray-agent.md), reality_short_ids,
                               sni, fingerprint, flow, network_type.

vless_credentials             NEW table, VLESS's analogue of VPNPeer. device_id is NOT
                               unique alone — UNIQUE(device_id, server_id) instead —
                               so a device can hold one credential per VLESS server,
                               which is what makes multi-node support (below)
                               representable without a later schema change.

Device.protocol                NEW column: wireguard | vless (default wireguard,
                               backfilled). Existing WG columns (public_key/
                               assigned_ip) stay None for VLESS devices.
```

Migration: `a1c9e7f3b246_add_vless_protocol_support` — verified end-to-end against a
real SQLite file via actual `alembic upgrade`/`downgrade` (not just
`Base.metadata.create_all`), including that pre-existing rows are correctly backfilled
to `wireguard` and a downgrade→re-upgrade round trip reproduces the identical schema.
Not independently verified against a real PostgreSQL instance in this environment (no
Docker available) — it follows the same `batch_alter_table` pattern already proven
against Postgres by `3073258ed68f`, and `tests/postgres/` will validate it for real on
the next CI run against the `postgres:16-alpine` service container.

## Server-side provider abstraction

`XrayAgentProvider` (`backend/app/services/vless/provider.py`) is a **separate**
Protocol from `VPNProvider`, not an extension of it — VLESS's actual operations
(UUID-keyed create/remove/rotate/list/health) are structurally different from
WireGuard's (peer create/delete/disable/enable/build-config), and forcing them into one
shared interface today would either bloat `VPNProvider` with VLESS-only concerns or
leave WireGuard-only concerns unused on a "VLESSProvider." Revisit only once a genuine
third exit-node protocol makes the real commonalities visible — not before.

## Subscription formatter

`VLESSFormatter` (`backend/app/services/subscription_delivery/formatters/
vless_formatter.py`) is likewise a separate class, not conforming to the same
`SubscriptionFormatter` Protocol `WireGuardFormatter` implements — that Protocol's
`render(peer, server, profile)` shape is single-peer and WireGuard-specific;
`VLESSFormatter.render(device, items)` takes a list of
`(VLESSCredential, VPNServer, VLESSServerConfig)` tuples so it can render **one line per
active credential**, which is what makes multi-node support additive later (see below)
rather than a rewrite. `SubscriptionDeliveryService.deliver()` dispatches to it directly
based on `device.protocol`, bypassing the WireGuard format registry entirely for VLESS
devices — a `?format=` override doesn't mean anything meaningful across protocols, so it
isn't honored there.

**Confirmed-safe minimum grammar** (see the research this is based on):
```
vless://<uuid>@<host>:<port>?encryption=none&security=reality&sni=<sni>&pbk=<reality-public-key>&fp=<fingerprint>&type=<network-type>&flow=<flow>#<device-name>
```
Deliberately excludes `node_id` (not part of the confirmed grammar) and `xtls=2`
(meaning/necessity never confirmed against official sources) — neither is invented.
`sid` is omitted entirely since every node's Reality config ships a single empty
shortId, making it always optional client-side.

## Reality key management

See docs/xray-agent.md's dedicated section — summary: the private key lives only on
the exit node's filesystem, generated once by Ansible, read directly by Xray-core;
only the public key (non-secret) ever reaches the backend, stored in
`VLESSServerConfig.reality_public_key`, read directly by `VLESSFormatter`. Because
`/sub/{token}` is live-fetched rather than pushed once, a client that refreshes after a
(rare, ops-triggered) key rotation picks up the new public key automatically — a
genuine advantage of the subscription-link model over a one-time push.

## Multi-node support (schema-ready, not yet auto-enrolled)

`vless_credentials`' `UNIQUE(device_id, server_id)` constraint and `VLESSFormatter`'s
per-credential loop already support a device holding N credentials across N servers —
`SubscriptionDeliveryService._deliver_vless` loads **every** active credential for a
device, not just one. MVP provisioning (`DeviceService._provision_vless`) only ever
creates one credential on one server (`pick_best_available`), and there is no
auto-enrollment logic that would create additional credentials on new nodes for
existing devices — that is a deliberate, explicit scope boundary for this
implementation, not an oversight. Adding a second node today requires: registering it
via `POST /api/v1/vless-servers`, and a decision (not yet built) about whether/how
existing devices get backfilled onto it.

## Scaling

Adding a VLESS node never invalidates existing subscription URLs — `/sub/{token}` is
live-fetched, not a one-time push, so a new node only affects devices a future
enrollment step (see above) actually attaches credentials to.

## Failure scenarios

| Scenario | Behavior |
|---|---|
| Xray-core crashes/restarts | xray-agent's periodic reconciliation (not just startup — see docs/xray-agent.md) repopulates the live user list without backend involvement |
| xray-agent crashes/restarts | systemd restarts it; startup reconciliation repopulates from its local desired-state store; existing connections through Xray are unaffected the whole time (xray-agent isn't in the data path) |
| Backend unavailable | Existing VLESS users unaffected (Xray keeps running); only new provisioning/disable/enable/revoke calls fail |
| xray-agent unreachable from backend | `HttpXrayAgentProvider` retries connection-level failures (not 4xx/5xx) up to 3 times; a still-failing call surfaces as `ExternalServiceError`/502, same shape as a WireGuard `vpn_agent_unreachable` failure |
| Node marked offline | `VPNServerService.pick_best_available(VLESS)` already excludes non-`online` servers, reusing the existing `VPNServerStatus` enum — no VLESS-specific mechanism needed |
| Subscription expired | Same authority as WireGuard: `SubscriptionExpiryWorker` → `DeviceService.disable_all_for_user` → `DeviceService.disable`, which now branches on `device.protocol` and removes the VLESS credential from Xray exactly as it disables a WireGuard peer — no second, independent expiry system |
| Device revoked while user still holds the link | `VLESSCredential.status` flips to `revoked`, removed from Xray; `/sub/{token}` returns the same generic 404 every other failure mode does (see docs/subscription-delivery.md's anti-enumeration property, unchanged and reused as-is for VLESS) |

## What is explicitly NOT implemented

- **Happ Smart Routing for VLESS** — the `happ://routing/onadd/<base64-JSON>` deeplink
  mechanism exists in Happ, but this implementation only renders full-tunnel `vless://`
  lines. `RoutingService`'s existing WireGuard `AllowedIPs` logic is completely
  untouched; no VLESS-side additive renderer was built.
- **Multi-node auto-enrollment** — see "Multi-node support" above.
- **Reality key rotation tooling** — see docs/xray-agent.md's "Known limitations."
- **A real end-to-end test against an actual Xray-core process or a real Happ client**
  — every test in this implementation runs against fakes (`FakeXrayAgentProvider`,
  `FakeXrayHandlerClient`) or an in-process fake gRPC servicer speaking the same trimmed
  proto (see docs/xray-agent.md). A real VPS running Xray-core, and a real Happ install
  actually importing a generated `vless://` link, are both required before calling this
  production-verified rather than architecture-and-wire-protocol-verified.
